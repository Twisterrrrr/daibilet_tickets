# Почему текущая админка не похожа на эталон admin-ux.lovable.app

> Дата: 2026-03-19

## 1. Контекст

- **Эталон:** https://admin-ux.lovable.app/admin/events — прототип админки, созданный в Lovable.
- **Текущая админка:** `packages/frontend-admin` — переработанная в феврале 2026 под shadcn/ui, TanStack Table, Recharts.
- **Дневник (Diary.md):** «Пользователь предоставил демо daibi.lovable.app/admin как эталон».
- **Факт:** Пользователь выгружал полную копию Lovable-проекта на Git — но в SPBBOATS её нет.
- **Найден репозиторий:** https://github.com/Twisterrrrr/event-horizon-hub — полный Lovable-проект (Admin + Supplier + Public).

---

## 2. Что произошло: Lovable-экспорт не был интегрирован

**По факту:** Lovable-проект выгружали в Git, но текущая админка в SPBBOATS **не основана** на этом коде.

В истории SPBBOATS видно:
- коммиты `chore(admin-ui): Prompt 3`, `Prompt 4`, `Prompt 5` — админку собирали через AI-промпты;
- `chore(shared-ui): skeleton backoffice ui` — создавали «скелет» с нуля;
- эталон Lovable использовался как **референс**, а не как исходный код.

То есть редизайн делали «похоже на Lovable», а не «на базе Lovable».

**Возможные причины:**
1. Lovable-экспорт попал в **другой репозиторий** (не SPBBOATS).
2. Экспорт был, но интеграция не планировалась — ожидали «переписать по мотивам».
3. Разная структура (Lovable → Supabase, SPBBOATS → NestJS) мешала прямому использованию.

---

## 3. Почему Lovable-код не «вшит» в проект

Lovable генерирует своё приложение. Результат на admin-ux.lovable.app — **отдельное приложение** с:

- своей структурой папок и компонентов
- своей версткой и стилями
- своей настройкой shadcn/Tailwind

Текущая админка Дайбилета **не копировала** этот проект. Она:

1. Заменяла старый UI (таблицы, inline-стили) на shadcn/ui.
2. Подключала существующий backend (NestJS).
3. Переносила уже реализованный функционал в новые компоненты.

Эталон использовался как **образец стиля**, а не как основа для реализации. В итоге получился «похожий по духу», но другой по деталям интерфейс.

---

## 3. Чем Lovable-приложения обычно отличаются

Типичные черты Lovable-приложений:

| Аспект | Lovable-стиль | Текущая админка |
|--------|----------------|-----------------|
| **Layout** | Макет часто генерируется целиком, единый шаблон страниц | Каждая страница собирается отдельно, шаблоны разные |
| **Sidebar** | Фиксированная ширина, чёткое визуальное разделение | Собственная реализация, другая структура меню |
| **Page header** | Часто крупный заголовок, явные кнопки действий | `PageHeader` из shared-ui, свои размеры и расположение |
| **Таблицы** | Компоненты из шаблонов Lovable | `DataTable` на TanStack Table, своя стилизация |
| **Фильтры** | Могут быть в сайдбаре, панели или верхней полосе | Отдельная Card над таблицей, inline-фильтры |
| **Отступы и сетка** | Одна система spacing для всего приложения | `PageContainer` max-w-6xl, px-4, py-6 |
| **Типографика** | Шрифты и размеры из шаблона Lovable | Стандартные Tailwind-классы |
| **Карточки** | Оформление карточек из Lovable | shadcn `Card` + свои классы |

## 4. Конкретные расхождения в `/admin/events`

### 4.1. Макет страницы

**В Lovable** обычно:
- единый блок: заголовок + фильтры + таблица в одном каркасе;
- или фильтры слева/сверху в отдельной зоне.

**У нас:**
```
PageHeader (title + actions)
  ↓
Card (фильтры) — отдельная карточка
  ↓
Card (таблица) или DataTable напрямую
```

### 4.2. Фильтры

**У нас:** все фильтры в одной Card, горизонтально, flex-wrap.

**В Lovable** может быть:
- коллапсируемая панель;
- вынос части фильтров в sidebar;
- иной порядок и группировка.

### 4.3. Таблица

**У нас:** `DataTable` с `ScrollArea`, своя пагинация, `Table` из shadcn.

**В Lovable:** может использоваться другой компонент таблицы с другой плотностью строк, высотой, отступами.

### 4.4. Сайдбар

**У нас:** своя навигация (каталог, поставщики, продажи и т.д.), своя иерархия пунктов.

**В Lovable:** своя структура меню и группировка.

### 4.5. Визуальный стиль

- Цвета: наши CSS-переменные (`--primary`, `--sidebar-*`) могут отличаться от палитры Lovable.
- Скругления: `--radius: 0.5rem` — могут быть другие значения.
- Тени: Lovable часто добавляет больше теней у карточек/модалок.

---

## 5. Почему так вышло

1. **Не было pixel-perfect референса** — эталон рассматривали как ориентир, а не как макет.
2. **Разная эволюция** — Lovable генерирует приложение целиком; наша админка развивалась постранично.
3. **Общий shared-ui** — один `PageHeader`, `PageContainer`, `DataTable` для админки и ЛК поставщика, без специальной «Lovable-версии».
4. **Функция важнее вида** — при редизайне в первую очередь переносили логику и поведение, а не точный визуал.

## 6. Что делать, чтобы приблизиться к эталону

### Вариант A: Визуальный референс

1. Сделать скриншоты admin-ux.lovable.app (страницы, сайдбар, таблицы, фильтры).
2. Выделить конкретные отличия: отступы, размеры, цвета, расположение блоков.
3. По шагам приводить страницы админки к этому виду (CSS, layout, компоненты).

### Вариант B: Использовать код Lovable

1. Экспортировать/скачать проект из Lovable (если есть такая возможность).
2. Перенести layout, sidebar и ключевые компоненты в `packages/frontend-admin`.
3. Подключить наши API и маршруты к этому UI.

### Вариант C: Точечные правки по страницам

1. Начать с `/events` как самой важной страницы.
2. Сравнить с эталоном и привести к нему:
   - PageHeader и блок действий;
   - блок фильтров;
   - таблицу (ячейки, пагинация, плотность).
3. Повторить для других основных страниц.

## 7. Если у вас есть Lovable-экспорт в Git

**Если выгруженная копия Lovable-проекта существует**, логичный шаг — использовать её как основу.

### 7.1. Репозиторий Lovable

**https://github.com/Twisterrrrr/event-horizon-hub**

Структура:
- `src/layouts/AdminLayout.tsx` — SidebarProvider, AdminSidebar, SidebarTrigger (collapsible)
- `src/components/admin/AdminSidebar` — навигация
- `src/components/ui/sidebar` — shadcn Sidebar (react-resizable-panels)
- `src/pages/admin/EventsListPage.tsx` — карточки фильтров, таблица, «Сбросить (N)»
- `src/data/mock.ts` — mock-данные (заменить на adminApi)

### 7.2. План интеграции

1. **Найти репозиторий/ветку** с Lovable-кодом.
2. **Сопоставить структуру:**
   - Lovable часто использует Supabase — наши API на NestJS;
   - заменить вызовы Supabase на `adminApi` к нашему backend.
3. **Подставить в монорепо:**
   - либо заменить `packages/frontend-admin` содержимым Lovable-админки;
   - либо вынести layout/sidebar/страницы из Lovable в наш frontend-admin.
4. **Подключить API:** заменить mock/ Supabase на реальные endpoints `/admin/*`.

### 7.3. Минимальный вариант

Если полная замена сложна — можно взять из Lovable-экспорта только UI:

- `Layout`, `Sidebar`, стили;
- `PageHeader`, `DataTable`, карточки;
- структуру страниц (без логики).

И подставить под наши API и маршруты.

## 8. Рекомендация

**При наличии Lovable-экспорта в Git:** Вариант B (использовать его код) — приоритетный.

**Если экспорт недоступен или интеграция слишком трудоёмка:** Вариант A (скриншоты + пошаговое приведение к эталону).
