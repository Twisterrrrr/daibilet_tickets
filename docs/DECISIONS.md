# Decisions — как фиксируем важные решения

**Назначение:** политика фиксации **значимых** решений (архитектура, контракты, фазы), чтобы они не терялись в переписке и не путались с «черновыми обсуждениями».

---

## 1) Где что пишем

| Тип | Где |
|-----|-----|
| Краткие записи по датам (наблюдения / решения / проблемы) | [`Diary.md`](Diary.md) |
| Архитектурные инварианты и границы системы | [`ARCHITECTURE.md`](ARCHITECTURE.md) + [`core/architecture.md`](core/architecture.md) |
| ADR-реестр (история) | [`archive/specs/ARCHITECTURE_DECISIONS.md`](archive/specs/ARCHITECTURE_DECISIONS.md) |
| Продуктовый «фундамент» и фазы Now/Next | [`PROJECT-FOUNDATION.md`](PROJECT-FOUNDATION.md) |

---

## 2) Формат ADR (когда заводим отдельную запись)

Рекомендуемый скелет:

1. **Контекст** — какая проблема / триггер.  
2. **Решение** — что делаем.  
3. **Альтернативы** — что отвергли и почему.  
4. **Последствия** — что меняется для кода, контрактов, эксплуатации.

Если решение **меняет публичный контракт API или схему БД** — обязательна ссылка на задачу в [`Tasktracker.md`](Tasktracker.md) и согласование с минимальным диффом.

---

## 3) Что не является «решением канона»

- разовые Cursor-промпты и черновики в `reports/` без переноса в разделы выше;
- длинные implementation notes — держим в [`archive/`](archive/) после выжимки смысла в активные документы.
