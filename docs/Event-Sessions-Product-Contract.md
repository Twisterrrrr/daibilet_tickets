# Event + Sessions — продуктовый контракт (черновик для эпика)

> **Статус:** зафиксировано на уровне продукта (вариант A), без привязки к текущим API. Документ **не меняет домен**: Prisma и публичные API уже разводят Venue и Event; задача контракта — **жёстко проговорить продуктовый язык** и запретить ошибочное слияние в эпике Event Master.  
> Для **Event:** один UX и один доменный контракт для **admin** и **supplier**; отличие — **RBAC** и объём полей. **Venue** — отдельная сущность (§6–7, §12), не режим события.  
> **Связь:** `Project.md` § Admin V2; `Diary.md` 03.04.2026 (вход в эпик + уточнения модели).

## 1. Роль продукта

- **Событие + сеансы + коммерция** — отдельный продукт внутри платформы, не «вкладка в оболочке V2».
- **Продажи без рассадки:** продаём **категории билетов**, не места в зале; нет seat-level, всё через **квоты (ёмкость)**.

## 2. Вкладки карточки события (логическая структура)

Порядок может уточняться в UX; смысл вкладок фиксирован.

### 2.1 Информация

**Смысл:** идентичность, контекст, базовый контент (главная вкладка при создании).

- Название, краткое и полное описание.
- **Тип события:** экскурсия / музей (арт) / мероприятие — определяет **набор тип-специфичных текстовых блоков** (см. §5).
- Город, локация, оператор.
- **Возрастное ограничение** (например: 0+, 6+, 12+, 16+, 18+) — фильтры, карточка каталога, может входить в quality score.
- **Длительность** — для разовых событий обязательна как смысловой атрибут.

### 2.2 Категории и цены

**Смысл:** коммерческая модель; **цена привязана к категории**, сеанс опирается на набор категорий, а не «цена на слот» как единственный источник.

По каждой категории (ticket category):

- Название (взрослый / детский / VIP и т.д.).
- **Цена** (`price`), **старая цена** (`oldPrice`) — только для **отображения** скидки на витрине; **не участвует в расчётах оплаты**. Если `oldPrice > price` — зачёркнутая цена и процент скидки.
- **Квота категории** — опционально; по умолчанию не задана; если задана — **потолок продаж по этой категории** (см. §3).
- Активность категории.
- **Самостоятельная / зависимая** категория (правила совместной покупки — детализировать при проектировании checkout).
- **Групповая категория:** `groupSize` — один купленный билет списывает **N мест** из квоты сеанса (см. §3.3).
- **Ограничение по дням недели** — категория **видна только** для сеансов, попадающих в выбранные дни (например «будни» Пн–Пт). Это **фильтр отображения и участия в продаже**, **не** правило пересчёта квоты.

### 2.3 Расписание

**Смысл:** временная модель; **режимная**, не один универсальный «редактор таблицы».

**Режим A — одиночный сеанс (разовое событие)**  
Если одна дата/время, нет повторяемости: **без развёрнутой таблицы** — поля: дата, время начала, длительность. В домене всё равно существует **ровно один сеанс**.

**Режим B — повторяющиеся сеансы**  
Сетка (дни недели + время), период действия, генерация слотов.  
**Два представления одного источника данных (обязательны):**

- **Таблица** — массовые операции, точное редактирование, фильтры.
- **Грид (календарь)** — визуальный обзор, поиск «дыр» в расписании.

**Режим C — открытая дата (open date)**  
Для музеев/площадок и т.п.: **нет фиксированных сеансов**; задаётся период действия (`validFrom` / `validTo`) и/или «действует **N** дней с момента покупки». Валидация входа: **дата покупки + идентификатор билета** на билете.  
**Правило совместимости:** в одном событии **не смешивать** open date и обычные сеансы — **лучше жёстко запретить** на уровне продукта, чтобы не ломать квоты и UX.

**Пер-сеансовые переопределения:** на уровне слота в расписании может задаваться **переопределение общей квоты события** (см. §3.2).

*Правила отмен, переносов сеансов, оповещения клиентов — отдельное обсуждение, не блокируют контракт вкладок.*

### 2.4 Продажи

**Смысл:** операционный контроль по событию.

- Отфильтрованная таблица покупок/билетов по **этому** событию.
- Действия: открыть PDF-билета, **переотправить** на другой e-mail (в рамках прав RBAC).

### 2.5 Медиа

Фото, видео, галерея.

### 2.6 SEO

- Автогенерация title / description с возможностью ручной донастройки позже.
- Slug и прочие поля — в соответствии с общей SEO-политикой проекта.

### 2.7 Качество

- Агрегированная оценка готовности карточки (например 0–100).
- Рекомендации и замечания.

## 3. Квоты — три уровня и приоритет

**Итоговая доступность** для продажи в контексте сеанса и категории (упрощённо):

`доступно = min(квота_сеанса, [квота_категории если задана]) − уже_продано_с_учётом_групповых_списаний`

Уточнения:

### 3.1 Общая квота события

Задаётся на уровне события по умолчанию; применяется ко всем сеансам, пока не переопределена.

### 3.2 Квота сеанса (slot override)

Задаётся на вкладке расписания для конкретного слота; **перекрывает** общую квоту события для этого слота.

### 3.3 Квота категории (опционально)

По умолчанию не задана. Если задана — ограничивает продажи **именно этой категории** (в дополнение к потолку сеанса).

### 3.4 Групповая категория

- Одна покупка по категории со `groupSize = N` списывает **N единиц** из квоты сеанса.
- Опционально: **лимит числа покупок категории** (`maxPurchasesPerCategory` или аналог).
- **Конфликт:** если осталось мест меньше, чем `groupSize`, покупка невозможна — поведение и подсказки в UI нужно заложить заранее.

### 3.5 Ограничение категории по дням недели

Только **видимость / участие в оффере** для сеансов в эти дни; не заменяет и не дублирует логику квот из §3.1–3.3.

## 4. Open date (без сеансов)

- Нет слотов → нет slot-level квот в привычном смысле; квота ведётся **глобально на продукт** и/или **по категориям** — детализация при техническом проектировании.
- На билете — усечённая информация для контроля (дата приобретения, ID).

## 5. Тип-зависимый и опциональный контент

### 5.1 Шаблон по типу события

Тип → набор рекомендуемых секций (не только «один текст»):

| Тип | Примеры блоков |
|-----|----------------|
| Экскурсия | программа, маршрут, что включено / не включено |
| Музей / площадка | экспозиция, правила посещения, часы работы |
| Мероприятие | программа, участники, условия входа |

Реализация может опираться на идею **template-конфига** (как в venue template), без привязки к конкретной схеме БД в этом документе.

### 5.2 Универсальные опциональные блоки (ContentBlock)

Структурированный контент, не произвольная простыня:

- **Поля:** `type` (ключевые моменты, особенности, транспорт, маршрут, стоит учесть, …), опционально `title`, `content`, `order`.
- Не обязательны; заполняются поставщиком и/или админом; влияют на конверсию, SEO и **quality score**.

## 6. Venue и Event — разные сущности (не «режим одной карточки»)

**Важно:** ранее обсуждался вариант «продукт = Event или Venue» с общим каркасом вкладок и скрытым «Расписанием» для площадки. После уточнения модели **это отвергнуто как описание домена**: **venue не является режимом события** и **не сливается с Event** в одну редактируемую сущность с флагом типа.

### 6.1 Что такое Venue

**Venue** — локация / площадка / **контейнер** контента и навигации.

- Может **существовать на витрине без собственных билетов** (информационная ценность: описание, адрес, правила, как добраться, медиа).
- Может **агрегировать связанные события** (текущие выставки, будущие мероприятия, постоянные экспозиции).
- **Опционально** может иметь **собственные продажи** (вход в пространство, open-date билет, и т.п.) — это отдельный коммерческий контур **на сущности площадки**, не «упрощённое событие».

**Публикация площадки** (`venue published`) и **публикация события** (`event published`) — **разные** состояния: площадка может быть активна в каталоге, а привязанные события — в черновике или наоборот.

### 6.2 Что такое Event

**Event** — конкретный **продаваемый или витринный продукт** с собственным контуром:

- своё расписание **или** open-date механика (§2.3, §4) — **внутри события** сеансы и open date **не смешивать**;
- свои категории и цены, квоты (§3–4), продажи, билеты;
- **привязка к venue** (где происходит), без отождествления с venue.

**Пример:** арт-пространство = **Venue**, выставка внутри него = **Event**.

### 6.3 Что не делаем

- Не объявляем **Venue = VENUE-режим Event** в мастере события.
- Не переключаем тип «событие ↔ площадка» после создания без отдельной **миграции продукта** (если вообще допустима).
- Не смешиваем в одном **Event** сеансы и open date (как раньше).

### 6.4 Паттерн «похожая оболочка» — допустим только на уровне UI

Допустимо переиспользовать **общий каркас интерфейса** (шапка, вкладки, SEO, медиа, качество, контентные блоки), но **смысл вкладок и доменные правила различаются**. См. §7.

### 6.5 Витринные типы площадки (продуктовая таксономия)

Одна сущность **Venue** на бэкенде может играть на витрине **разные продуктовые роли** (без смены сущности):

| Тип | Смысл на витрине | Связанные Event | Блок «Программа» | Продажи |
|-----|------------------|-----------------|------------------|---------|
| **A. Место как главная сущность** (standalone) | Карточка локации самодостаточна: музей/парк/смотровая/каток/зоопарк и т.д. | Не обязательны; дочерние продукты могут отсутствовать | Опционален или вторичен | Собственный билет площадки (open date и т.п.) или **вовсе без продаж** |
| **B. Хаб программы** (program hub) | Площадка — контейнер для сменных продуктов: арт-пространство, культурный центр, выставочная площадка | **Важны**: афиша / текущие–будущие–прошедшие | Блок **«Программа»** (как `GET /venues/:slug/program`) — ключевой | Могут сочетаться с входным билетом на пространство |

**Пограничный случай:** концертная площадка с афишей — пересекается с типом B; приоритет блока «Программа» vs общий каталог событий **уточнять по продукту** (изначально программа заточена под музеи/арт; см. `Venue-Program-UX.md`).

**Жёсткое правило для эпика Event + Sessions:** мастер события и редактор сеансов проектируются **только для сущности Event**, не для Venue и не как «универсальный мастер продукта с режимами».

## 7. Редактор площадки (отдельный эпик)

Мастер **Event + Sessions** (этот документ, §2–5) **не расширяется** на полное редактирование venue; у площадки — **свой** продуктовый поток и набор вкладок.

**Логичный набор вкладок Venue (черновик):**

- Информация (место, адрес, оператор, правила посещения и т.д.)
- Контент (в т.ч. `ContentBlock`, тип-специфичные секции для «места»)
- Медиа
- **Связанные события** (список/привязка Event)
- **Продажи / билеты** — вкладка **только если** у площадки включены собственные офферы; иначе скрыта или пустое состояние
- SEO
- Качество

**Переиспользуем без дублирования «второго админки»:** общий **page shell**, примитивы вкладок, SEO, медиа, качество, блочный контент.

**Не переносим механически с Event:** вкладку **Расписание** в том же виде; **квоты сеанса**; массовые операции по слотам; синхронизацию расписания с внешними источниками как у события. Собственные билеты площадки (если есть) опираются на **модель времени площадки** (фиксированный период / валидность N дней с покупки) и **квоты без слота** — детализация в спецификации редактора Venue, не в §3 настоящего документа.

## 8. Границы эпика «Event + Sessions»

- Эпик покрывает **только сущность Event**: мастер, режимы расписания и open date **внутри события**, категории, квоты события/сеанса, продажи по событию, связь с venue как **поле привязки**.
- **Редактор Venue**, продажи «входа в пространство» и агрегация событий на странице площадки — **отдельные задачи**; публичный PDP venue см. также `Project.md` § Venue PDP и `Landings-Architecture.md` при необходимости.

## 9. Общий слой admin + supplier (для Event)

- Один сценарный и визуальный язык **для карточки Event** (§2–5); различие — **RBAC** и допустимые действия.
- Для **Venue** — тот же принцип «один UX-язык между admin и supplier», но в рамках **отдельного** эпика редактора (§7).

## 10. Критические зоны риска (для проектирования и тестов)

1. **Конфликты квот:** квота категории визуально «больше» квоты сеанса; групповой билет не помещается в остаток.
2. **Смешение open date и сеансов** в одном событии — избегать (запрет).
3. **Скрытие категории** по дням недели — пользователь должен понимать причину (**UI-хинт** в админке/ЛК).
4. **Перепродажа (oversell)** при конкуренции запросов и holds — явная транзакционная модель на стороне API/БД.
5. **Правила отмен/переносов и коммуникации с клиентами** — отдельный подэпик, но не противоречащий квотам и статусам билетов.
6. **Путаница Venue и Event:** попытка сделать venue «режимом» мастера события ломает публикацию без билетов, хаб событий и независимые жизненные циклы — **держать границу сущностей** (§6–8).

## 11. Следующий шаг проектирования и приоритет эпика

**Логичный порядок:** сначала **закрыть механику создания события и расписания (sessions)** для режима **SCHEDULED** — это **ядро**, от которого зависят почти все event-сценарии с слотами (в т.ч. выставки с сеансами, экскурсии, массовые операции, issues в админке). Без устойчивого контура «событие ↔ сеансы ↔ квоты слота» остальное (категории, checkout, open date, сценарный сид) опирается на шаткий фундамент.

Рекомендуемая последовательность:

1. **P0 — Event + Sessions (scheduled):** мастер/редактор создания и правки события в части **идентичности + расписание** (включая разовый слот и повторяющуюся сетку, таблица + календарь, пер-сеансовые квоты по §3.2), согласование с существующими admin API сеансов и правилами публикации; общий слой admin + supplier по §9.
2. **P1 — Категории и цены ↔ сеансы ↔ holds/checkout** (§2.2, §3, граничные случаи) — после того как слоты стабильны.
3. **P1 — Режим OPEN_DATE внутри Event** (§2.3 C, §4) — отдельный UX-поток, но тот же эпик Event, не Venue.
4. **Параллельно по мере необходимости:** сценарный сид §12, продажи/билеты по событию §2.4, SEO/медиа/качество как следующие слои мастера.
5. **Venue** (§7, §6.5) и отдельный `Venue-Editor-*` — **после** или параллельно только ресурсами, **без** блокирования P0.

- По **Venue (документация):** короткий продуктовый документ или раздел: собственные офферы, квоты без слота, связанные события, публикация без продаж; витринные типы §6.5 — когда эпик редактора площадки встанет в работу.

**План внедрения (этапы M/R, моки V2, аудит кода):** [Event-Master-Implementation-Plan.md](./Event-Master-Implementation-Plan.md).

## 12. Данные для разработки и тестов: базовый сид vs сценарный

**Наблюдение:** основной `seed` и пост-скрипт `prisma/seed-venue-links.ts` **корректно отражают домен** (отдельные Venue/Event, справочники подкатегорий, пример OPEN_DATE у площадки, привязка `venueId`). Но **не заменяют** осмысленный продуктовый набор данных для UX и эпика Event + Sessions.

**Что делает текущий post-seed (упрощённо):** привязка существующих событий к площадкам **по ключевым словам в title** (случайный набор в пределах лимита), плюс демо **входного билета** для Эрмитажа. Это **склейка данных**, а не сценарий «площадка → предсказуемая программа выставок».

**Почему это слабо для продукта:** блок программы площадки (`buildVenueProgramEventWhere`: `venueId` + подкатегория **EXHIBITION** и т.д.) **не наполняется** целенаправленным сидом; проверить **current / upcoming / past**, edge cases и нагрузку на мастер события по таким данным нельзя.

**Рекомендуемая стратегия (два слоя):**

1. **Базовый сид** — как сейчас: справочники, массовые площадки, импорт/типовые события, минимальная склейка.
2. **Сценарный сид** (отдельный скрипт или флаг) — **фиксированные** объекты, например:
   - площадка-хаб (например арт-пространство «Гараж»);
   - **Event 1:** выставка **SCHEDULED** с сеансами и категориями;
   - **Event 2:** выставка **OPEN_DATE**, постоянная/с периодом;
   - **Event 3:** экскурсия по выставке — сеансы, категории, квоты;
   - при необходимости — входной билет площадки с **несколькими категориями** и квотами (расширение демо из `seed-venue-links`);
   - явные `venueId`, `subcategories`, `dateMode` — **без** привязки по keywords.

**Итог:** архитектура данных уже правильная; **слой сценарных фикстур** нужен, чтобы продукт и UX не расходились с «система работает на случайных данных». Задача в бэклоге: `seed-scenario-venue-events` (см. `Tasktracker.md`).
