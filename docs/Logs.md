# Логи (Admin V3) — MVP и расширение (2026-04)

Документ описывает, что такое «Логи» в Admin V3, какие источники событий целесообразно собирать, и какой **минимальный** функционал реализован сейчас.

---

## 1. Цель

«Логи» — это **единая точка для расследования инцидентов** и контроля операций:

- понять **кто** и **когда** менял сущности в админке;
- быстро увидеть цепочку «изменение → эффект» (например, настройки/каталог/публикация);
- иметь безопасный «след» по интеграциям и платежам, не трогая production‑логи приложения.

Ключевой принцип: **не хранить секреты** и не превращать UI в дамп всех payload’ов.

---

## 2. Источники событий (что собирать)

### 2.1. AuditLog (изменения в админке) — **MVP**

Источник: таблица `audit_logs` (Prisma `AuditLog`), запись через `AuditInterceptor` для `/admin/*` POST/PATCH/PUT/DELETE.

Поля:
- `createdAt`, `userId`, `action`, `entity`, `entityId`, `before`, `after`.

Это «скелет» всей системы логов: если нет аудита — невозможно расследовать большинство проблем.

### 2.2. PaymentEventLog / ProcessedWebhookEvent (платежи и вебхуки)

Источники:
- `PaymentEventLog` (raw webhook payload, получено);
- `ProcessedWebhookEvent` (результат обработки + трассировка к `PaymentIntent`).

Что важно в UI:
- provider + eventType + providerEventId/paymentId;
- статус обработки (success/ignored/failed) и error;
- ссылка на связанный `PaymentIntent` / `CheckoutSession` / `RefundRequest` (если есть).

Payload показывать **по запросу** (детальная карточка), а не в списке.

### 2.3. ProviderWebhookLog (интеграции провайдеров билетов)

Источник: `provider_webhook_logs`.

Что важно:
- provider, processingStatus, receivedAt/processedAt;
- errorMessage / notes;
- idempotency/correlation ключи, если они есть в headers/meta.

### 2.4. Возвраты (RefundRequest) — как «события домена»

Пока возвраты живут как доменные статусы. Для расследований полезно показывать:
- кто инициировал (USER/ADMIN/SYSTEM);
- цепочку статусов и timestamps;
- связанный платеж/интент.

Это можно сделать как отдельную вкладку в «Логах», без введения новой таблицы «refund_events» (на первом этапе).

---

## 3. Безопасность и приватность

- **Не показывать**: токены, ключи, cookies, credentialsJson интеграций.
- **PII** (email/phone) — только если это осознанно разрешено политикой доступа; по умолчанию в логах лучше опираться на `id` и entity links.
- Payload для вебхуков — показывать только **админам**, и лучше в режиме «копировать» + «маскирование полей».

---

## 4. Реализовано сейчас (MVP)

### 4.1. Admin V3 UI

- Меню: **Система → Логи** (`/admin-v3/logs`).
- Список: **AuditLog** с фильтрами:
  - `entity`, `entityId`, `userId`, `action`, `q` (по entity/entityId/action) и период `from/to`.
  - пагинация.
  - раскрытие `before/after` JSON на строке.

### 4.2. Backend API

Используется существующий эндпоинт:
- `GET /api/v1/admin/audit` (role `ADMIN`)

Дополнительно расширено:
- фильтры `q`, `from`, `to`.

---

## 5. Что дальше (бэклог)

- Вкладки **Платежи** (PaymentEventLog/ProcessedWebhookEvent) и **Интеграции** (ProviderWebhookLog).
- Детальная карточка записи лога по `id`, с безопасным предпросмотром payload.
- RBAC: отдельная роль «Viewer» для чтения логов без доступа к чувствительным payload.
