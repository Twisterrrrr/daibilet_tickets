## Phase 2: Supplier Orders / Booking Operations

### Цель
Дать поставщику полный контроль над заказами по его событиям: просмотр, поиск, подтверждение/отмена, работа с претензиями.

### Scope

**Supplier Portal (frontend-supplier):**
- Страница «Заказы» с фильтрами: дата, событие, статус (PENDING / CONFIRMED / CANCELLED / COMPLETED)
- Таблица: дата, клиент (анонимизированный), событие, оффер, сумма, статус
- Drawer/модальное окно детали заказа: контакты, состав корзины, история статусов
- Действия: подтвердить, отклонить (с причиной), пометить выполненным

**Admin Panel:**
- Унификация OrdersList с паттерном PageHeader + DataTable + фильтры
- Видимость dispute/issue по заказу (если есть ReviewDispute, Support-тикет)
- Переход из заказа в CheckoutSession / PaymentIntent для техподдержки

### Технические требования
- API `GET /supplier/orders` — выборка по operatorId, пагинация, фильтры
- API `POST /supplier/orders/:id/confirm` / `reject` — state machine OrderRequest
- Существующие модели: CheckoutSession, OrderRequest, PaymentIntent (supplierId уже есть)
- Возможно потребуется view/agg для «заказ с точки зрения поставщика» (одна строка = один Package/OrderRequest с привязкой к событиям оператора)

### Зависимости
- PaymentIntent с `supplierId` — уже есть
- OrderRequest state machine — готов
- Нет: отдельная таблица SupplierOrder не нужна, работаем с CheckoutSession + OrderRequest

### Риски
- Смешанная корзина (события от разных операторов) — один CheckoutSession может содержать офферы нескольких поставщиков; UI/фильтрация по «моим» заказам должна учитывать это

### Definition of Done
- Поставщик видит список своих заказов, фильтрует, открывает детали
- Может подтвердить/отклонить заявку; статус синхронизируется с OrderRequest
- Админ видит связь заказ ↔ dispute/support

## Phase 3: Availability / Sessions / Inventory

### Цель
Управление доступностью и расписанием: сеансы, даты, количество мест. Критично для MANUAL-событий и тех провайдеров, где мы держим инвентарь.

### Scope

**Supplier Portal:**
- Страница «Доступность» / «Календарь» — календарный вид или список сессий по событию
- CRUD сессий: дата, время, вместимость, базовая цена (если отличается от offer)
- Bulk-операции: «добавить 10 дат», «отключить серии»

**Admin Panel:**
- Диагностика: «пустые» события (нет сессий), просроченные сессии, конфликты
- Возможность ручной правки сессий при сбоях

### Технические требования
- Модель EventSession — уже есть (startsAt, capacity, priceFrom, offerId)
- API `PUT /supplier/events/:eventId/sessions` — уже частично есть
- UI для:
  - просмотра сессий по eventId
  - добавления/удаления сессий
  - редактирования capacity, price (если MANUAL)
- Синхронизация с внешними системами (TC, Teplohod) — read-only для sync-источников; редактирование только для MANUAL

### Зависимости
- EventSession, EventOffer в Prisma
- TcSync / TepSync — не трогаем, для MANUAL/Partner — ручное управление

### Риски
- Противоречие sync vs ручное: при sync TC/Teplohod перезаписывают сессии — для MANUAL такого нет
- Partitioning EventSession по startsAt (см. Project.md) — при росте объёма

### Definition of Done
- Поставщик управляет сессиями MANUAL-событий через UI
- Админ видит отчёт «события без сессий» и может диагностировать проблемы

## Phase 4: Listing Health / Quality Layer

### Цель
Скоринг качества листинга (события, площадки, офферы) и прозрачная панель «здоровья» для поставщика и админа.

### Scope

**Supplier Portal:**
- Панель «Здоровье листинга»:
  - отсутствующие фото, описание < N символов, нет расписания, нет цены
  - доля отклонённых событий, черновиков «зависших» > 7 дней
  - рекомендации: «добавьте фото», «заполните описание»

**Admin Panel:**
- «Качество каталога»: агрегат по городу, категории, поставщику
- «Здоровье поставщика»: сводка по всем событиям оператора
- Экспорт/отчёт для редакторов

### Технические требования
- Сервис `ListingHealthService`:
  - правила скоринга (наличие полей, длина, сессии, цены)
  - кеш/материализованный скоринг — при росте объёма
- API `GET /supplier/listing-health` — сводка по operatorId
- API `GET /admin/catalog/health` — сводка по фильтрам

### Зависимости
- Event, EventOffer, EventSession, Venue — структура полей
- Trust system (Phase 1) — Catalog block уже учитывает качество; Phase 4 — отдельный UX-слой

### Риски
- Перегрузка при пересчёте на каждый запрос — нужен batch-job или кеш

### Definition of Done
- Поставщик видит «здоровье» своих листингов и получает actionable рекомендации
- Админ имеет отчёт по качеству каталога

## Phase 5: Supplier Analytics

### Цель
Аналитика для поставщика и админа: выручка, заказы, топ-события, тренды. Основа для бизнес-решений.

### Scope

**Supplier Portal:**
- Отчёты:
  - выручка за период (по дням, по событиям)
  - количество заказов, средний чек
  - топ-N событий по выручке и по количеству заказов
  - тренды: сравнение периодов (неделя к неделе, месяц к месяцу)
- Экспорт CSV/Excel

**Admin Panel:**
- Отчёты по поставщикам, городам, категориям
- Сводные дашборды: GMV, конверсия, доля по источникам

### Технические требования
- `GET /supplier/reports/sales` — уже есть каркас (Partner API)
- Расширить: группировки по eventId, cityId, дате; фильтры
- `GET /admin/reports/*` — агрегаты по operator, city, category
- Возможно: материализованные views или pre-aggregated таблицы для быстрых дашбордов

### Зависимости
- PaymentIntent (PAID), CheckoutSession, Event, Operator
- Ledger — если используется для финансовой отчётности

### Риски
- Объём данных: при росте — индексы, партиционирование, кеш

### Definition of Done
- Поставщик строит отчёты по продажам и экспортирует
- Админ видит сводную аналитику по платформе

---

### UX Note: DateRangePicker (Supplier/Admin)

- Для всех фильтров по датам (supplier Reports, admin Checkout/Reports) используется единый компонент `DateRangePicker` из `@daibilet/shared-ui`.
- Поведение:
  - 2 месяца рядом (desktop), 1 месяц на мобильных.
  - Локаль `ru-RU`, понедельник — первый день недели.
  - Формат инпута: `DD.MM.YYYY — DD.MM.YYYY`.
  - Быстрые пресеты: «Сегодня», «Неделя», «Месяц».
- В ЛК поставщика `Reports` компонент уже заменяет пару `input type=date` и использует выбранный диапазон для параметров `from`/`to` в отчётах и CSV-экспорте.

## Phase 6: Pricing & Promotions

### Цель
Rule-based скидки и промо без динамического ценообразования: промокоды, early bird, last minute, featured placements.

### Scope

**Supplier Portal:**
- Управление промокодами: код, скидка (%, фикс), условия (eventId, даты)
- Early bird / last minute: правила «за N дней до события» / «за N часов»

**Admin Panel:**
- Модерация промо: approval промокодов
- Featured placements: ручной boost событий на главной / в категориях

### Технические требования
- Модель PromoCode (code, type, value, conditions, operatorId, validFrom/To)
- Применение при Checkout: проверка в PaymentService
- Модель FeaturedPlacement (eventId, slot, priority, validFrom/To) — для админки

### Зависимости
- Checkout flow, PaymentIntent
- Явно не делаем: динамическое ценообразование, A/B цен

### Риски
- Конфликт промо (несколько применимых) — политика: один промокод на заказ, или приоритет

### Definition of Done
- Поставщик создаёт промокоды; они применяются при оплате
- Админ модерирует и управляет featured-событиями

## Phase 7: Ranking / Merchandising

### Цель
Управление выдачей: boost, подавление, featured. Подсказки поставщику по видимости.

### Scope

**Admin Panel:**
- Ручной boost: приоритет события в выдаче по городу/категории
- Подавление: скрытие низкокачественных без удаления
- Featured-слоты (связь с Phase 6)

**Supplier Portal:**
- Подсказки: «ваше событие на 3-м месте в категории», «добавьте фото для повышения ранга»

### Технические требования
- Скоринг выдачи: уже есть зачатки (badges «Оптимальный выбор»)
- Расширить: manualBoost, suppressLowQuality
- API каталога: учитывать boost при сортировке
- Listing Health (Phase 4) — входные данные для «качество влияет на ранжирование»

### Зависимости
- Phase 4 (Listing Health)
- Phase 5 (частично — данные для рекомендаций)

### Риски
- Сложность скоринга: не перегружать MVP; начать с простых правил (ручной boost + базовый score)

### Definition of Done
- Админ может boost/подавить событие
- Поставщик видит подсказки по улучшению видимости

## Phase 8: Integrations / Extension Points

### Цель
Точки расширения для sync, availability, price, bookings. Без реализации полноценного partner ecosystem.

### Scope

**Supplier Portal:**
- Страница «Интеграции»: статус подключений (TC, Teplohod, Partner API)
- Маппинг внешних систем: какие события откуда пришли
- Webhook-статус (если есть)

**Платформа (Backend):**
- Extension points:
  - `SyncAdapter` — интерфейс для новых источников каталога
  - `AvailabilityProvider` — опциональный слой «где брать доступность»
  - `BookingProvider` — опционально для прямых бронирований
- Документация для разработчиков: как подключить новый провайдер

### Технические требования
- Абстракции (интерфейсы) в backend
- Конфиг: какие провайдеры активны
- UI — read-only статус, без глубокой настройки

### Зависимости
- Текущие TcSync, TepSync — рефакторинг в адаптеры (по желанию)

### Риски
- Переусложнение: не строить «плагин-систему», только чёткие extension points

### Definition of Done
- Есть документированные extension points
- Поставщик видит статус своих интеграций

## Phase 9: Team / Roles / Support

### Цель
Мультипользовательский доступ, роли, центр поддержки. Масштабирование работы поставщиков и админов.

### Scope

**Supplier Portal:**
- Приглашение пользователей: email, роль (OWNER, MANAGER, CONTENT, ACCOUNTANT)
- RBAC: кто что может (события, офферы, отчёты, настройки)
- Центр поддержки: тикеты, FAQ, статус

**Admin Panel:**
- Supplier support operations: связь тикет ↔ заказ ↔ поставщик
- Audit trail: кто что изменил (event, venue, order)

### Технические требования
- SupplierUser — уже есть, роли в enum
- API приглашений: POST /supplier/invitations, активация по ссылке
- Проверки ролей в SupplierController (Guards)
- Support: интеграция с существующей Support-системой админки

### Зависимости
- Operator, SupplierUser
- Support (тикеты) — уже есть в админке

### Риски
- Миграция: один владелец → несколько пользователей — обратная совместимость

### Definition of Done
- Поставщик приглашает коллег с разными ролями
- Админ ведёт support-операции и видит audit trail
