# Admin V3 — Настройки: подход к UX

Документ фиксирует **договорённости по интерфейсу** раздела «Настройки» в `frontend-admin-v3` при доведении до **функционального паритета с V1** (`frontend-admin`), без изменения контрактов API. Визуальный ритм, PageHeader, состояния загрузки/ошибок и табы — в духе общего референса [admin-v3-ux.md](./admin-v3-ux.md).

---

## 1. Контекст: что есть в V1 и чего не хватает в V3

| Область | V1 | V3 (текущее) |
|--------|-----|----------------|
| Статус синхронизации + метрики (события/сессии, last ops) | Да | Нет |
| Операции: full/incr sync, retag, populate combos, flush cache | Да | Нет |
| Конфигурация цен (pricing) | Да | Нет |
| Feature flags | Да (toggle сразу) | Да (черновик + сохранить — **UX богаче**) |
| SEO / System KV | Да, с **ограничением редактирования в UI** по роли | Да, без явного disabled по роли |
| Пользователи админки (список, роль, активность) | Да | Нет |

**Вывод:** V3 сейчас — осознанный узкий MVP (flags + app KV). Цель этого документа — описать, **как** добавить остальное, не превращая экран в «простыню» и не ломая привычки команды.

---

## 2. Принципы UX для экрана «Настройки»

1. **Одна точка входа** — маршрут «Настройки» остаётся единым; внутри — **вкладки (tabs)**, а не бесконечный скролл как единственная навигация. Длинные подразделы не смешиваем на одной плотной странице без структуры (как в V1 это уже тяжело для восприятия).
2. **Группировка по смыслу и риску:**
   - **Наблюдение и инфраструктура** — синхронизация и операции (чтение статуса + кнопки действий).
   - **Бизнес-параметры** — ценообразование (редко меняется, нужна ясная форма).
   - **Поведение продукта** — feature flags.
   - **Контент и публичный образ** — SEO.
   - **Системное поведение сайта** — System KV.
   - **Доступ** — пользователи админки.
3. **Опасные действия** — sync, retag, populate, flush cache: визуально отделены (карточка/секция с предупреждением), по возможности **подтверждение** перед запуском (особенно full sync и flush cache с выбором namespace). Текст ошибки с бэкенда показываем явно (как в V1 через toast/алерт).
4. **Согласованность с V1 по правам (RBAC в UI):** как в V1, поля SEO/System и действия, которые в V1 были только для `ADMIN`/`OWNER`, в V3 должны быть **read-only или скрыты** для `EDITOR`/`VIEWER` — опираемся на `GET /auth/me` (роль). Пока запрос не подтянулся — не давать ложного ощущения редактируемости (skeleton или disabled форма).
5. **Обратная связь:** успех/ошибка — через существующие паттерны V3 (toast при необходимости + инвалидация React Query). После ops — **обновление статуса** синхронизации (как в V1 после `runOps`).
6. **Не дублировать отдельные маршруты без нужды:** в V1 pricing может жить отдельным URL; в V3 достаточно **вкладки** «Цены», если нет отдельного требования к deep link. При появлении требования к URL — добавить подмаршрут `/settings/pricing` позже.

## 3. Рекомендуемая структура вкладок (IA)

Порядок слева направо — от **операционки** к **конфигу** и **людям** (можно скорректировать после ревью):

| Вкладка (рабочее название) | Содержимое |
|----------------------------|------------|
| **Синхронизация и операции** | Блок «Статус» (как V1) + блок «Операции» (кнопки + select namespace для flush). |
| **Цены** | Форма pricing (поля как V1), одна кнопка «Сохранить». |
| **Feature flags** | Текущая панель V3 (черновик + сохранить). |
| **SEO** | Текущая форма + read-only/disabled по роли для не-ADMIN/OWNER. |
| **System** | Аналогично SEO. |
| **Пользователи** | Таблица пользователей + смена роли/активности как в V1 (с учётом прав на бэкенде). |

**Альтернатива (если вкладок слишком много):** объединить «Синхронизация и операции» и «Цены» в одну вкладку «Инфраструктура и цены» двумя карточками — допустимо, если команда предпочитает меньше табов.

## 4. Детали по разделам

### 4.1 Синхронизация и операции

- Статус: те же поля, что V1; при `lastError` — заметное предупреждение.
- Кнопки: подписи на русском или как в API (как договоримся в UI-копирайте); loading — per-action.
- Flush cache: сохранить выбор namespace; destructive-стиль кнопки.

### 4.2 Цены

- Сохранение одним действием; после сохранения — обновление локального состояния из ответа (как V1).

### 4.3 Пользователи

- Таблица: email, имя, роль, активность, последний вход — как минимум паритет с V1.
- Ограничения по редактированию — по политике бэкенда; в UI не показывать недоступные контролы или disabled с подсказкой.

---

## 5. Связь с технической реализацией (без смены контрактов)

- Использовать **те же эндпоинты**, что V1:  
  `sync-status`, `ops/*`, `pricing`, `feature-flags`, `app/seo`, `app/system`, `users`, `auth/me`.
- Клиент: расширить `modules/settings/api/settings.ts` (или вынести ops/pricing/users в соседние модули по принятой в проекте структуре), **React Query** для загрузки и инвалидации.

## 6. Открытые вопросы (зафиксировать перед разработкой)

1. Финальный набор вкладок: **6 табов** или **объединение** «Синхронизация + Цены»?
2. Подтверждения: **только** для flush и full sync или для всех ops?
3. Нужен ли **deep link** только на «Пользователей» или достаточно одного `/settings`?
4. Копирайт кнопок ops: оставить англ. ярлыки как в V1 или везде RU?

После ответов этот раздел можно сократить или удалить.

## 7. План внедрения (черновик для Tasktracker)

1. API-слой: типы + функции для sync-status, ops POST, pricing GET/PATCH, users GET/PATCH, `auth/me`.
2. Общий хук или query `useAdminMe()` для RBAC на SEO/System (и при необходимости на других вкладках).
3. UI: новые вкладки и секции по IA выше; опасные действия с подтверждениями по согласованию.
4. Регрессия: сравнение поведения с V1 на одной среде (одинаковые роли).
5. Документация: краткая отметка в `Project.md` / трекере при принятии паритета.
