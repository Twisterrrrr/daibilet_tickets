# Паритет узкого лендинга «ужин на теплоходе»: Lovable ↔ Дайбилет

> **Назначение:** зафиксировать **построчный** разбор эталона (HTML/React Lovable, маршрут вида `/events/dinner-cruise/moscow`) и текущей реализации **городского каталожного лендинга** Дайбилета (`/cities/:citySlug/:landingSlug`).  
> **Продуктовая рамка:** это **query-scoped landing** — одна узкая тема, **табличная выборка** по одному намерению, а не широкий каталог.  
> **Связанные документы:** [`landing-reference-pages.md`](landing-reference-pages.md), [`page-anatomy.md`](page-anatomy.md), [`Landing-Composition-System.md`](Landing-Composition-System.md) § «Частные особенности отдельных лендингов».

**Якорь задачи в трекере:** `landing-lovable-dinner-parity`

---

## 1. Эталонные точки в коде Дайбилета

| Область | Путь / компонент |

## 2. `<head>` / SEO / разметка

| Элемент Lovable | Статус в Дайбилете | Что нужно для паритета |
|-----------------|-------------------|-------------------------|
| Уникальные `<title>` и `meta description` под запрос | Частично: `generateMetadata` в `page.tsx` из `metaTitle` / `metaDescription` / fallback | Дисциплина контента в CMS; при необходимости отдельные поля под OG |
| `og:title` / Twitter = смыслу страницы | Зависит от заполнения лендинга | Выравнивание с H1 в админке / шаблон мета |
| Массив **JSON-LD `FoodEvent`** по каждому предложению | **Нет** в стандартном рендере лендинга | **Новая разработка:** серверный компонент или генерация в `generateMetadata` / отдельный скрипт из вариантов (`startsAt`, место, цена, описание) — нужен стабильный маппинг полей |

## 3. Hero

| Элемент Lovable | Статус | Комментарий / пробелы |
|-------------------|--------|------------------------|
| Крошки: `Главная → Речные прогулки (ссылка на вертикаль) → тема` | **Иначе** | Сейчас: `Главная → город → фрагмент H1`. Нет обязательной ссылки на хаб вертикали (`/river-cruises/:city` и т.п.) — см. политику URL в `Landings-Architecture.md` |
| H1 + подзаголовок | Покрыто | `landing.title`, `landing.subtitle` |
| Три чипа в одной строке (N рейсов / продано / рейтинг) | **Иначе** | `CatalogLandingHero`: блок справа «Проверенные организаторы» + список; смысл близок (`total`, `stats.totalSold`, `stats.avgRating`), **layout не как в Lovable** |
| CTA вниз к офферам | Покрыто | Ссылка на `#variants`; текст отличается («Смотреть рейсы» и т.д.) |

## 6. Фильтры и сортировка (`LandingClient` + `FilterBar`)

| Фича Lovable | Покрыто `LandingClient` | Нужны данные / доработка |
|--------------|---------------------------|---------------------------|
| Табы: цена / рейтинг / время | Да (`sort`: `price`, `popular`, `time`) | — |
| Даты: сегодня / завтра / календарь | Да (при `timeSlotMode !== 'hidden'`) | Массив `filters.dates` из API |
| **Тип меню** (любое / сет-меню / фуршет) | **Нет** | Новый фасет: теги события или поле в read-model; расширение `FilterState` + логика фильтрации |
| **Время суток** (закат 18–21 / ночь 21+) | **Частично** | Сейчас слоты **night** (мосты) и **evening** (интервалы `ev-*`), не маппинг «закат/ночь» как в макете — либо новый `timeSlotMode`, либо новые коды слотов |
| Дропдауны «Формат» и «Цена» | **Частично** | Цена и причал есть; отдельного **«формата круиза»** (классический / VIP / панорамный) **нет** — нужен атрибут в данных или тег |
| Сброс фильтров | Да | — |
| Адаптив (десктоп / мобильные ряды) | Своя вёрстка `FilterBar` | Пиксельный паритет с Lovable не требуется для MVP |

## 8. Таблица сравнения (`ComparisonTable`)

| Колонка / поведение Lovable | Дайбилет | Пробел |
|-----------------------------|----------|--------|
| **Теплоход** (название + судно + причал) | Колонки: **Время** \| **Причал / оператор** (адрес + эвристика судна из `title`) | Другой порядок колонок; судно из **парсинга** `extractVessel(title)`, не структурированное поле |
| **Меню** (тип + строка блюд) | Колонка **«Опции»**: длительность, рейтинг, места | **Нет** колонки меню и блюд — нужны `menuKind`, `menuSummary` / теги или обогащение от поставщика |
| **Цена** | Есть | Копейки, подпись «взрослый» |
| **Время** (час + длительность) | В первой колонке + дата | Семантически ок, расклад отличается |
| **Формат** (романтический / VIP / панорамный) | **Нет** | Поле/тег `experienceFormat` или аналог |
| Бейдж «Лучший выбор» | «Оптимальный» в строке | Покрыто (`bestDealIdx`) |
| Мало мест / нет мест | Плашки по `availableTickets` | Покрыто |
| CTA «Забронировать» | TC widget / teplohod link | Покрыто для поддерживаемых источников |

**Шаблон данных:** `templateType === 'COMPARISON_TABLE' | 'HYBRID'` включает таблицу; паритет с гастро-колонками потребует **расширения строки**, не только переключателя шаблона.

## 10. Данные API / событие — что добавить для «гастро-таблицы»

Минимальный набор для устойчивого паритета **без эвристик только по названию**:

1. **`menuKind`** (или набор тегов): фуршет / сет-меню / «любое меню».
2. **`menuSummary`** — краткий список блюд или строка для колонки «Меню».
3. **`experienceFormat`** (или теги): классический / романтический / VIP / панорамный и т.д.
4. Согласованная модель **вечернего слота** под фильтры «закат / ночь» или явное правило по `startsAt` + TZ города.
5. Опционально **`vesselName`** (или нормализованное поле), чтобы не полагаться на `extractVessel(title)`.

Источник: поставщик (TC/teplohod), ручной тег в админке, или derived layer поверх существующих текстов — решение фиксируется отдельно (без ломки публичного контракта без миграции).

## 11. Критерии приёмки (MVP паритета UX)

- [ ] Лендинг под один запрос с **`COMPARISON_TABLE`** (или гибрид) и заполненным контентом в CMS.
- [ ] Крошки и перелинковка согласованы с каноном URL (вертикаль «речные» vs город) — отдельное решение продукта.
- [ ] Либо колонки «Меню» / «Формат» в таблице на основе **явных полей/тегов**, либо зафиксированный план этапа 2.
- [ ] JSON-LD для ключевых офферов — отдельная задача (см. §2).
- [ ] Мобильная версия: горизонтальный скролл таблицы или карточный режим — согласовать с `templateType` и дизайном.
